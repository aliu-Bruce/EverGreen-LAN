# EverGreen LAN 架构

本文记录已经做出的设计决策、支撑它们的事实，以及刻意没有做的事。代码变了先改这里。

## 1. 不变量

这四条是硬约束，任何实现都不能违反：

1. **数据面没有中转。** 游戏流量只存在于两端之间的加密 UDP 里。不经过我们的服务器，也不经过任何对端的服务器。
2. **没有常驻基础设施。** 项目本身不运营任何服务；删掉仓库，已经连上的房间照常工作。
3. **握手必须双向认证。** 只拿到邀请码的人才能连上；主机必须能证明自己是邀请码里那个公钥的持有者。
4. **失败要说人话。** 打洞失败就明说失败，绝不偷偷降级成中转。

## 2. 为什么没有「房间号」

Radmin VPN 那类产品可以输入「网络名 + 密码」加入，是因为厂商的协调服务器知道谁在哪个网络里，替双方交换地址和公钥。**流量**确实是 P2P 的，但**控制面**离不开那台服务器。

如果要「零服务器」，连接信息就必须随邀请码一起带出来。于是：

| 方案 | 需要服务器 | 加入方式 | 采用 |
|---|---|---|---|
| 房间号 + 协调服务 | 是 | 输名字 | ✗ |
| 邀请码 | 否 | 粘贴 / 扫码 | ✓ |

代价是加入时要复制一段字符串。这是有意的取舍，不是未完成的功能。

## 3. 协议

### 3.1 邀请码

```
EGL1-<base64url_nopad(zlib(bincode(InviteCode)))>
```

`InviteCode` 字段：

| 字段 | 长度 | 作用 |
|---|---|---|
| `version` | 1 | 格式版本，当前 1 |
| `room_id` | 16 | 房间标识，同时作为 Noise prologue |
| `name` | ≤48 | 房间显示名 |
| `psk` | 32 | 房间密钥，Noise PSK |
| `host_pub` | 32 | 主机静态公钥，用于认证主机 |
| `host_ip` | 4 | 主机虚拟地址，固定 `10.66.0.1` |
| `candidates` | ≤16 | 主机候选 `ip:port`，拒绝域名 |
| `created_at` | 8 | 创建时间 |

编码后约 180–250 字符。解码时校验：版本、字段长度、候选地址可解析、非全零、主机地址必须在虚拟网段内。解压上限 8 KiB，防解压炸弹。

**候选地址只接受字面量 `ip:port`**，不接受域名——邀请码必须在不联网、不解析的情况下可用。

**候选地址必须真的可达。** 一开始我们取「默认路由的本地地址」，结果在这台装了 Clash 类代理的机器上
拿到的是 `198.18.0.1`——代理 TUN 的假 IP，发给朋友等于给了一个只在本机存在的地址。现在枚举所有网卡并过滤：

| 过滤掉 | 原因 |
|---|---|
| `127.0.0.0/8` | 回环 |
| `169.254.0.0/16` | 链路本地，通常是没有 DHCP 的空网卡 |
| `10.66.0.0/16` | 我们自己的虚拟网卡 |
| `198.18.0.0/15` | 保留给基准测试，实际被代理 TUN 当作假 IP |
| 未启用 / 已断开的网卡 | 连不上 |

绑定到具体地址时（测试、或用户指定网卡）则直接用该地址，不枚举。

### 3.2 握手

使用 `Noise_IKpsk0_25519_ChaChaPoly_BLAKE2s`。

> **踩过的坑**：最初写成 `psk2` 并按三条消息驱动，结果处处 `HandshakeAlreadyFinished`。原因是
> **IK 是两条消息的握手模式**（`<- s` 之后 `-> e, es, s, ss` 与 `<- e, ee, se`），而 `psk2`
> 指向第三条消息，在 IK 里根本不存在，密钥矩阵被静默跳过。现在改为 `psk0`：房间密钥在第一条
> 消息之前就混入，主机可以**在付出任何昂贵计算之前**直接丢弃没有邀请码的握手包。

一次往返建立会话：

```
guest                         host
  |  -> e, es, s, ss            |
  |                             |
  |  <- e, ee, se               |
  |                             |
  [双方进入 transport 模式]
```

- `IK` 让客户机确认对端持有邀请码里的公钥，落点不可被中间人替换。
- `psk0` 让主机确认对端持有房间密钥。
- `room_id` 作为 prologue，房间之间不可串话。
- 传输层用 Noise `TransportState`，每条消息自带 nonce 与 Poly1305 认证标签，重放会被拒绝（已有测试）。

### 3.3 帧

每个 UDP 数据报 = 一条 Noise 密文 = 一个帧。首字节是类型：

| tag | 帧 | 载荷 |
|---|---|---|
| 0x01 | `Hello` | 虚拟 IP、角色、名字 |
| 0x02 | `HelloAck` | 分配的虚拟 IP、主机名 |
| 0x03 | `Ip` | 原始 IPv4 包 |
| 0x04 | `Ping` | 序号 |
| 0x05 | `Pong` | 序号 |
| 0x06 | `Bye` | 原因 |

`Ip` 帧是最热的路径，因此不做 bincode 包装：一个字节的 tag 加上原始包。

### 3.4 打洞

1. 主机在邀请码里放入**所有**候选：物理网卡地址、STUN 得到的公网映射。
2. 客户机**同时**向所有候选发包，每 300 ms 一轮，最多 10 轮。
3. 主机的回包从哪个地址回来，就认哪个。
4. 只接受来自已拨候选 IP 的回复，避免被无关扫描包干扰。

Windows 在端口关闭时会把 ICMP unreachable 表现为下一次 `recv_from` 返回 `WSAECONNRESET`，这被专门识别为「此路不通，换下一个」，而不是整体失败。

## 4. 虚拟网络

| 项 | 值 | 原因 |
|---|---|---|
| 网段 | `10.66.0.0/16` | 足够大且不易与家用网段冲突 |
| 主机地址 | `10.66.0.1` | 固定，便于邀请码不携带分配逻辑 |
| 客户机地址 | `10.66.0.2` 起 | 由主机在 `HelloAck` 中告知 |
| MTU | 1200 | 低于 IPv6 最小 MTU，规避奇怪路径 |
| 隧道开销 | 17 字节 | tag + Poly1305 标签 |

### 4.1 广播与组播

Minecraft Java 的「对局域网开放」会周期性向 `224.0.2.60:4445` 发送：

```
[MOTD]玩家名 - 世界名[/MOTD][AD]端口[/AD]
```

接收方监听到就把游戏显示在多人列表里。要让它跨越互联网，需要三件事：

1. **路由**：`224.0.2.60/32` 指向虚拟网卡。`10.66.0.0/16` 的定向广播
   `10.66.255.255` 由地址分配自动产生，无需额外配置。
2. **复制**：路由器识别目的地址是组播或广播时，把它复制给房间内**每一个**对端，
   而不是只发给某一个。
3. **注入**：对端把包写进自己的虚拟网卡，源地址改写成发送方的虚拟 IP，
   本机 Minecraft 就像收到局域网广播一样。

这套逻辑是通用的：任何使用组播或定向广播发现局域网游戏的程序都因此受益，
不需要为每个游戏写适配。

### 4.2 单播

目的地址是某个对端的虚拟 IP 时，直接封装成 `Ip` 帧发过去。目的地址是自己的，
丢弃（不应由 TUN 回环）。

## 5. 安全模型

**信任的边界是邀请码。** 持有邀请码 = 房间成员，这是设计意图。

| 威胁 | 缓解 |
|---|---|
| 中间人 | Noise IK：客户机校验主机静态公钥 |
| 陌生人扫端口 | `psk0`：无邀请码的连接在第一条消息就被丢弃 |
| 重放 | Noise 传输 nonce 单调，重放解密失败 |
| 篡改 | Poly1305 认证标签 |
| 邀请码泄露 | 无解——它就是钥匙。UI 明确提示不要公开分享 |
| 虚拟网段被滥用 | 只转发虚拟网段内的目的地，不提供出口节点能力 |

**不做的事**：不实现「退出节点 / 全流量代理」，避免被当成翻墙工具滥用。

## 6. 已知失败模式

| 现象 | 原因 | 处理 |
|---|---|---|
| 打洞失败 | 双方均为对称型 NAT | 提示用户；可选 UPnP 端口映射兜底 |
| 连不上但 ping 通 | 防火墙拦截 | 安装时添加私有网络入站规则 |
| 虚拟网段不通 | 代理软件 TUN 模式抢占路由 | 检测到冲突时提示为 `10.66.0.0/16` 配直连 |
| 网卡创建失败 | 未提权 | 启动时 UAC，未提权则明确告知不能用 |
| MC 看不到房间 | `224.0.2.60` 路由缺失 | 启动房间时校验路由存在 |

## 7. 房间运行时

`crates/evergreen-lan-room` 把三样东西缝在一起：虚拟网卡、隧道、路由。

```
       操作系统网络栈
             │ 原始 IPv4 包
      ┌──────▼──────┐        ┌────────────┐        ┌─────────┐
      │   Wintun    │◀──────▶│    hub     │◀──────▶│   UDP   │
      └─────────────┘        └────────────┘        └─────────┘
```

**hub 是一个单任务**，独占所有 Noise 会话。这是被迫的：Noise 传输态需要顺序调用，
Wintun 的接收也要求同一时刻只有一个读者。单任务同时消灭了锁竞争。

**设备解耦**：hub 从不直接碰 Wintun，只通过两个 channel 收发。这让整条数据通路
可以在没有驱动、没有管理员权限的情况下测试——这正是 `evergreen-lan-room` 那 9 个集成测试
能跑真实 UDP 握手、真实加密转发的原因。

**会话要点**：

| 事项 | 做法 |
|---|---|
| 握手 | 主机在 `select!` 里内联处理 m1→m2，成本低于 1ms |
| 地址分配 | 主机从 `10.66.0.2` 顺序发放，`Hello`/`HelloAck` 往返确认 |
| 保活 | 每 10s `Ping`，45s 无音讯判定离线 |
| 广播 | 复制给每个对端，各自一份密文 |
| 越界 | 目的地不在 `10.66.0.0/16` → 直接丢弃，不转发 |
| 拆解 | `Drop` 顺序：先撤路由，再关网卡，最后通知对端 |

**已验证（mock 设备 + 真实 loopback UDP）**：单向与双向单播、多对端的 MC 广播复制、
访客广播回传主机、发往公网被丢弃、发给自己的包被丢弃、地址顺序分配与名字同步、
错误邀请码被拒绝。

**未验证**：真实 Wintun 网卡的创建、`netsh` 地址/路由落地、真实网卡上的包收发。
这三项都需要管理员权限，是当前唯一的验证缺口。

### 7.1 拓扑：星形，但像交换机

房间是**星形**：每个访客只与主机建立一条隧道，访客之间没有直接会话。

这是一个刻意的取舍：

| | 全互联（mesh） | 星形（当前） |
|---|---|---|
| 握手次数 | N²，每对都要独立打洞 | N |
| 对打洞成功率的要求 | 每一对都必须成功 | 只有主机需要可被连接 |
| 主机带宽 | 只承载自己的流量 | 承载所有访客互访流量 |
| Minecraft 场景 | 多余 | 完全够用（客户端只连服务端） |

因为只有主机需要「好打洞」的 NAT，星形显著提高了成功率——家庭宽带的对称 NAT 只影响它自己能不能被连上，
而不是影响任意两个人之间能不能互通。

为了让星形用起来像交换机，主机做了两件事：

1. **中继广播**：访客 A 的 `224.0.2.60` 公告，主机在本地注入后还会转发给其余所有访客，且**不回传给发送者**。
2. **路由单播**：访客 A 发给访客 B 的包，主机按目的虚拟 IP 转发过去。

访客侧对应地实现**网关语义**：目的地址在虚拟网段内、但本地没有对应会话时，一律交给主机，
由主机决定投递或丢弃。这样访客不需要知道任何其他人的地址。

代价很诚实：主机上行带宽承载全部互访流量，8 人以内没问题，再大就该考虑全互联了。
